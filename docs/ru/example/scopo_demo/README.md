Все семейства скоупов рядом, с консолью, показывающей, что каждое из них
делает, пока оно это делает.

```sh
cd example/scopo_demo
flutter run
```

## Устройство

Девять вкладок: по одной на семейство плюс два сценария, которым нужен
отдельный экран:

| вкладка | что показывает |
| --- | --- |
| ScopeWidget | скоуп над собственными параметрами виджета и попараметрные подписки |
| ScopeModel | владение обычным объектом: `create`/`dispose`, `.value`, именованный скоуп |
| ScopeNotifier | то же для `Listenable`, где селекторы отсеивают лишние перестроения |
| AsyncScope | асинхронные инициализация и утилизация без контейнера |
| AsyncDataScope | то же, но с производимым значением, которое читает поддерево |
| LiteScope | класс состояния с полным жизненным циклом |
| Scope | полное семейство: дерево зависимостей, прогресс по каждой, состояние |
| Deferred closing | `close()`: экран закрытия поверх замороженного поддерева |
| NavigationNode | вложенный `Navigator`, чьи маршруты остаются внутри скоупа |

Под каждой демонстрацией — **консоль**. Она печатает вызовы жизненного цикла
скоупов этой вкладки по мере того, как они происходят: монтирование,
инициализация, прогресс, готовность, утилизация, утилизирован. В этом и смысл
приложения: порядок этих строк и есть то поведение, ради которого пакет
существует, а увидеть его иначе трудно.

## Три примера на каждой асинхронной вкладке

На вкладках AsyncScope, AsyncDataScope, LiteScope и Scope по три примера, и
разница между ними — это и есть весь урок:

1. **без `scopeKey`** — пересоздание скоупа запускает новый, пока старый ещё
   утилизируется; в консоли видно, как они накладываются;
2. **с `scopeKey`** — новый скоуп ждёт в очереди, и в консоли видно, что он
   стартует только после того, как предыдущий закончил;
3. **`scopeKey` + родитель и ребёнок** — родительский скоуп дожидается ребёнка,
   прежде чем утилизироваться, поэтому на выходе строки идут «изнутри наружу».

У каждого примера есть кнопка, пересоздающая его скоуп, — так и получаются три
последовательности выше.

## Deferred closing и NavigationNode

**Deferred closing** — это `close()` с заметной задержкой: готовое поддерево
замораживается снимком, поверх рисуется экран закрытия, а кнопка возвращает
управление, только когда утилизация закончена. На эту вкладку стоит посмотреть
до того, как применять `close()` всерьёз.

**NavigationNode** открывает экраны, диалоги и шторки через вложенный
`Navigator` и позволяет им читать скоуп, лежащий выше, — чего корневой
навигатор приложения не умеет. Дочерний экран читает счётчик из скоупа, который
живёт вне маршрута.
