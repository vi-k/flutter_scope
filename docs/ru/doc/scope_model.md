# ScopeModel

> Перевод `doc/scope_model.md` (blob `828155bcb3ef660376933bc35744a0df759e4042`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

Скоуп, который владеет одним обычным объектом Dart и отдаёт его своему
поддереву. Ни асинхронной фазы, ни контейнера зависимостей, ни класса
состояния: объект создаётся, когда скоуп встал на дерево, и освобождается, когда
он с дерева ушёл.

Берите его для всего, чем должно владеть дерево, но за чем никто не наблюдает
автоматически, — репозиторий, контроллер, сервис, модель формы. Когда объект
является `Listenable` и его изменения должны сами доходить до поддерева, берите
тему `ScopeNotifier`: это то же семейство плюс подписка.

## Три уровня

| класс | когда |
| --- | --- |
| `ScopeModel<M>` | обычный случай: виджет с `create`, `dispose` и `builder` |
| `ScopeModelBase<W, M>` | свой именованный скоуп со своими аксессорами |
| `ScopeModelCore<W, E, M>` | свой элемент; основа двух предыдущих |

### ScopeModel

```dart
ScopeModel<Cart>(
  create: (context) => Cart(),
  dispose: (cart) => cart.close(),
  builder: (context) => const CartScreen(),
);
```

`builder` намеренно получает только контекст. Этот контекст принадлежит
элементу скоупа, поэтому модель уже доступна через `ScopeModel.of` и
`ScopeModel.select` — с теми же правилами поиска и подписки, которыми
пользуются потомки. `dispose` работает на другом конце жизненного цикла, вне
сборки; элемент уже владеет ровно той моделью, которую создал, и потому
передаёт этот экземпляр колбэку напрямую, вместо того чтобы заставлять код
утилизации искать его через дерево.

`create` выполняется один раз, после монтирования элемента и до первой сборки
его поддерева. Если он бросает исключение, для скоупа это конец: `create`
больше не вызывают, и скоуп показывает ошибку вместо своего поддерева.
`dispose` вызывается при снятии элемента с дерева и только для действительно
созданной модели: неудачный `create` передавать нечего. `context`, который
получает `create`, — собственный элемент скоупа, поэтому из него можно
прочитать скоуп-предка — `ScopeModel.of<Session>(context, listen: false)`, —
но только с `listen: false`: `create` зовут один раз и больше никогда, поэтому
подписка, взятая оттуда, перестраивала бы поддерево вокруг значения, которое
осталось прежним. Это ловит `assert`.

`ScopeModel.value` принимает модель, которой владеет кто-то другой:

```dart
ScopeModel.value(value: cart, builder: (context) => const CartScreen());
```

У этого конструктора вовсе нет `dispose`, и это не упущение: кто объект создал,
тот его и освобождает. Скоуп лишь предоставляет его.

Потомки читают модель теми же тремя аксессорами, и здесь они возвращают саму
модель, а не контекст:

```dart
final cart = ScopeModel.of<Cart>(context, listen: false);
final total = ScopeModel.select<Cart, int>(context, (cart) => cart.total);
```

### ScopeModelBase

Наследуйтесь, когда скоуп заслуживает имени и собственного словаря:

```dart
final class CartScope extends ScopeModelBase<CartScope, Cart> {
  const CartScope({
    super.key,
    super.tag,
    required super.create,
    required super.dispose,
    required super.child,
  });

  @override
  Widget build(BuildContext context) => child;

  static Cart of(BuildContext context) =>
      ScopeModelBase.of<CartScope, Cart>(context, listen: false).model;

  static int totalOf(BuildContext context) =>
      ScopeModelBase.select<CartScope, Cart, int>(
        context,
        (scope) => scope.model.total,
      );
}
```

Два отличия от `ScopeModel` стоит заметить. `build` теперь ваш, поэтому скоуп
сам решает, что показывает, вместо того чтобы принимать `builder`. И аксессоры
базового класса возвращают `ScopeModelContext<W, M>` — элемент, — так что
селектор читает `scope.model`, а не модель напрямую. Обёртки в именованные
статики прячут обе детали от места вызова.

Под всем этим лежит `ScopeModelCore` — на случай, когда заменить нужно сам
элемент; `ScopeNotifier` и есть ровно такой случай.

## Кто кого уведомляет

За моделью не наблюдают. Ничто внутри неё не может сообщить скоупу, что что-то
изменилось: изменение поля `Cart` само по себе не дойдёт ни до одного потомка.

Скоуп уведомляет на собственном перестроении: когда родитель перестраивает
виджет `ScopeModel`, зависимых уведомляют, а их селекторы решают, кого
действительно перестроить. Поэтому изменившееся значение должно пройти через
виджет:

```dart
ScopeModel.value(value: cart, builder: (context) => const CartScreen());
```

с `StatefulWidget` сверху, который держит `cart` и зовёт `setState`: модель
остаётся тем же объектом, виджет скоупа перестраивается, и за ним следуют только
те потомки, у которых изменилось выбранное значение.

Если это читается как обходной путь — так и есть: модели, которая меняется сама,
место в `ScopeNotifier`, где `notifyListeners()` становится уведомлением без
всякого перестроения сверху. `ScopeModel` — для объектов, которые либо не
меняются, либо меняются только вместе с деревом над ними.

## Время жизни

`create` зовут из `init()` после монтирования элемента, до первой сборки
поддерева, так что успешно созданная модель готова для всего, что под ней.
Брошенный `create` терминален: второй раз его не зовут.

`dispose` зовут из `dispose()` элемента, после того как базовый класс отработал
свой разбор. Утилизатор элемента работает и после неудачной инициализации, но
сам `dispose` зовут только для модели, которую скоуп действительно создал:
модель из `.value` и брошенный `create` не трогают.

Время жизни привязано к элементу, а не к виджету. Скоуп, перестроенный с новыми
параметрами, сохраняет свою модель; скоуп, убранный с дерева, её теряет.
Перемещение скоупа с `GlobalKey` перемещает элемент, а с ним и модель.

На то же время жизни закреплён и конструктор, которым скоуп создан. У
перестроения, меняющего `ScopeModel(create:)` на `ScopeModel.value` или
обратно, честного ответа нет: придя к владеющему конструктору, владеть нечем —
`create` выполняется один раз и уже не выполнился; уходя от него, сделанную
этим скоупом модель освобождать всё ещё ему, а виджета, который говорит, кто её
освобождает, уже нет. Поэтому такое перестроение отклоняет ассерт. Дайте
виджету другой `Widget.key` — фреймворк построит новый элемент под новый
режим.

Утилизация здесь синхронная. Когда для освобождения объекта нужен `await`, это
не то семейство: `LiteScope` даёт состояние с `disposeAsync`, а `Scope` —
контейнер зависимостей, чей `dispose` дожидаются; и оба заставляют родителя
подождать свои дочерние скоупы, прежде чем разбирать себя.

## В отладчике

Элемент добавляет модель в свою диагностику, поэтому `debugDumpApp()` и
инспектор виджетов показывают рядом со скоупом `model: Cart(3 items)` — то, что
вернёт `toString` модели.
