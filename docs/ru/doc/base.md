# base

> Перевод `doc/base.md` (blob `445c11bba2246071fffd776e2367d368c866a517`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

Каждое семейство скоупов этого пакета — `ScopeWidgetBase`, `ScopeModel`,
`ScopeNotifier`, `AsyncScope`, `AsyncDataScope`, `AsyncControllerScope`,
`LiteScope` и `Scope` — стоит на одних и тех же трёх типах. Вместе они говорят, что такое скоуп для дерева
виджетов: `InheritedWidget`, который можно найти снизу, элемент, владеющий тем,
что скоуп держит, и один протокол поиска, общий для всех.

| тип | что это |
| --- | --- |
| `ScopeInheritedWidget` | `InheritedWidget`, от которого происходит виджет любого скоупа |
| `ScopeContext` | протокол поиска: `of`, `maybeOf`, `select` |
| `ScopeInheritedElement` | что обязан предоставить элемент скоупа |

Приложение их не создаёт. Читать этот слой всё же стоит, и по двум причинам:
здесь решается разница между `of`, `select` и `listen: false` — одинаково во
всех семействах, — и здесь же лежит контракт, который реализуют, когда пишут
свой скоуп.

## Виджет

```dart
abstract base class ScopeInheritedWidget extends InheritedWidget {
  final Object? tag;

  const ScopeInheritedWidget({super.key, this.tag, super.child});
}
```

`tag` называет конкретный скоуп. Два скоупа одного типа иначе неразличимы в
выводе, где скоуп без тега выглядит как `CounterScope(#4e0b7)`, а с тегом — как
`CounterScope(cart)`; формат описан в теме `debug`. Параметр `tag` пробрасывает
в этот конструктор каждое семейство, так что тег можно повесить на любой скоуп.

Про `child` нужно предупредить отдельно: это не то, что скоуп показывает.
Обычный `InheritedWidget` оборачивает переданное ему поддерево; скоуп строит
своё через `buildChild()` — отсюда берутся ветки ожидания, инициализации,
ошибки и закрытия у старших семейств. Конструктор всё же принимает `child`,
поэтому семейство, которому нужно обычное поведение, может его передать и
использовать из `buildChild()`; в пакете так не делает никто. Значение по
умолчанию — заглушка, которая отказывается создавать элемент вовсе: если скоуп
всё-таки построит этот `child` вместо своего, поломка будет немедленной, а не
незаметной.

## Элемент

```dart
abstract interface class ScopeInheritedElement<W extends ScopeInheritedWidget>
    implements ScopeContext<W> {
  W get widget;

  @mustCallSuper
  void init();

  @mustCallSuper
  void dispose();

  Widget buildChild();
}
```

`init()` выполняется один раз, после монтирования элемента и до его первого
`buildChild`. Если он бросает исключение, для скоупа это конец: хук больше не
вызывают, скоуп показывает ошибку вместо своего поддерева, и каждая следующая
сборка сообщает ту же ошибку. `dispose()` вызывается при снятии элемента с
дерева, и после неудачного `init()` тоже — попытка, сорвавшаяся на полпути,
могла уже что-то взять, и отдаётся это здесь, поэтому утилизатор семейства
обязан быть готов к частично инициализированному скоупу. Оба помечены
`@mustCallSuper`: семейство, которое их переопределяет, продолжает жизненный
цикл, а не подменяет его. Смонтированный элемент уже подключён к предкам,
поэтому из `init()` можно найти скоуп-предок с `listen: false`; подписка из
этого хука не поддерживается, и об этом говорит `assert`. Всё, чем скоуп
владеет, — модель, подписка на notifier, контейнер зависимостей, место в
очереди `scopeKey`, — берётся в первом и освобождается во втором.

Элемент заодно является `ScopeContext` собственного скоупа: именно этот объект
получает потомок из `of`, и поэтому `select` умеет читать текущее значение прямо
из него.

Весь учёт за этим — подписки по каждому зависимому, перестроение, которое только
уведомляет вместо перестроения поддерева, — живёт в `ScopeWidgetElementBase` и
описан в теме `ScopeWidget`. Реализовывать `ScopeInheritedElement` с нуля не
предполагается; предполагается наследоваться от того класса.

## Поиск скоупа

Три входа, все статические на `ScopeContext`, где `W` — тип виджета, а `C` —
тип контекста семейства:

```dart
ScopeContext.maybeOf<W, C>(context, listen: false); // C?, null, если не найден
ScopeContext.of<W, C>(context, listen: false);      // C, бросает, если не найден
ScopeContext.select<W, C, V>(context, selector);    // V, бросает, если не найден
```

На практике их зовут через обёртку, которую предоставляет каждое семейство, —
так параметры типов остаются короткими и верными:

```dart
final config = ScopeWidgetBase.of<ApiConfig>(context, listen: false);
final apiKey = ScopeWidgetBase.select<ApiConfig, String>(
  context,
  (widget) => widget.apiKey,
);
```

Сам поиск — это `getElementForInheritedWidgetOfExactType<W>()`: только предки и
**точный** тип. Скоуп, объявленный как `class CartScope extends ShopScope`, по
запросу `ShopScope` не найдётся. Поиск сам по себе ничего не перестраивает; на
что подписывается вызывающий, решает аргумент ниже.

## listen и его цена

`listen: false` находит скоуп и не подписывается ни на что. Вызывающего никогда
не перестроят из-за этого скоупа. Это то, что нужно коду вне `build`:
обработчику кнопки, который тянется к сервису, колбэку, который один раз читает
текущее состояние:

```dart
onPressed: () => ScopeModel.of<Cart>(context, listen: false).clear(),
```

`listen: true` подписывает на **любое** изменение этого скоупа. Зависимого
перестраивают всякий раз, когда скоуп уведомляет, независимо от того, изменилось
ли то, что зависимый читает.

`select` подписывает на одно значение и является причиной, по которой скоуп
дёшево обслуживает большое поддерево. Параметра `listen` у него нет — выбирать
и значит слушать, — и нет варианта с `maybe`: отсутствующий скоуп здесь ошибка,
а не `null`.

## Что на самом деле делает select

```dart
final userName = ScopeModel.select<Session, String>(
  context,
  (session) => session.userName,
);
```

Селектор выполняется сразу, а пара `(значение, селектор)` сохраняется как
подписка зависимого. Когда скоуп потом уведомляет, каждая сохранённая пара
каждого зависимого вычисляется заново: зависимого перестроят, только если хотя
бы для одной из них `selector(scope) != value`. Виджет, выбравший `userName`,
проспит изменение `cartTotal`.

Пять следствий стоит держать в голове.

**Сравнение идёт через `!=`**, то есть всё решает `==` выбранного значения.
Выбирайте поле, запись или неизменяемое значение. Селектор, который на каждом
вызове собирает новый `List` или новый объект, всякий раз оказывается не равен
прежнему, и виджет перестраивается так, будто ничего не выбирал.

**Селекторы накапливаются.** Несколько вызовов `select` в одном `build` создают
несколько подписок, и изменение в любой из них перестроит виджет один раз. Три
поля модели — это три `select`, а не один селектор, возвращающий три значения
списком: почему список хуже, сказано выше.

**`of(..., listen: true)` перебивает любой `select` в том же `build`.** Он
подписывает на всё, а подписку на всё нельзя сузить, добавив к ней селектор, —
в любом порядке виджет окажется перестраиваемым на каждое уведомление. Для
одного скоупа в одном `build` выбирайте что-то одно.

**Захваченное значение обновляется на каждой сборке.** Подписки
устанавливаются заново, пока зависимый строится, как и везде во Flutter, — так
что скоуп сравнивает с парой из последней сборки зависимого, а не из первой.

**Подписку можно брать только из сборки**, и об этом говорит ассерт. То, что
запросил зависимый, помнится в разрезе сборки, а граница между сборками взята
по кадру — хука «зависимый сейчас начнёт строиться» у Flutter нет. Поэтому
регистрация, сделанная вне сборки, попадает к той сборке, с которой делит
кадр, и стирается первой сборкой, которая кадр не делит:
`didChangeDependencies` идёт в том же кадре, что и следующая за ним сборка, —
`select` оттуда выглядит работающим и исчезает на первой же пересборке,
пришедшей от родителя, а не от изменения. Чтобы реагировать на изменение, а не
показывать его, держите подписку в `build`, а из `didChangeDependencies`
читайте скоуп с `listen: false`.

**Билдер `LayoutBuilder` считается сборкой**, и билдеры `OrientationBuilder` и
`SliverLayoutBuilder` тоже: они вызываются из `performLayout`, внутри сборки
собственного элемента, и то, что они возвращают, — поддерево этого элемента.
`select` оттуда работает как любой другой, и ассерт его пропускает.
Единственное место, где он больше не отличает ошибку от приёма, —
`didChangeDependencies` виджета, который сам находится под layout-колбэком.

## Зависимость от себя

Элемент скоупа может подписаться на собственный скоуп — так старшие семейства
перестраивают своё же поддерево по ходу инициализации. `InheritedElement` это
запрещает (ассерт в `notifyClients` блокирует зависимость от себя), поэтому
такие подписки хранятся отдельно от остальных и уведомляются отдельно. Механизм
принадлежит `ScopeWidgetElementBase`; здесь он важен лишь как причина, по
которой `ScopeInheritedElement` — интерфейс, реализуемый семейством, а не
миксин, который подмешивает приложение.

## Ошибки

Обе неудачи — обычные исключения, называющие запрошенный тип:

```text
Exception: CounterScope not found in the context
```

`of` или `select` не нашли виджет выше контекста. Либо скоупа там правда нет,
либо контекст принадлежит виджету над ним, а не под ним — обычная ошибка здесь
это поиск из того самого `build`, который скоуп и устанавливает. `maybeOf` в
той же ситуации вернёт `null` и годится там, где отсутствие ожидаемо.

Поиск с `listen: true`, ничего не нашедший, всё равно запоминается как
зависимость — ровно так же, как его запомнил бы штатный
`dependOnInheritedWidgetOfExactType`. Виджет, спросивший, когда скоупа над ним
не было, и позже перенесённый под скоуп по `GlobalKey`, получит
`didChangeDependencies` и спросит снова.

```text
Exception: The element of ScopeModel<Counter> is not ScopeModelContext<ScopeModel<Counter>, Counter>
```

Виджет нашёлся, но его элемент — не тот тип контекста, который запросили. Это
несовпадение параметров типов: аксессор одного семейства применили к скоупу
другого.

## Аксессоры и шаблоны для редакторов

Каждое семейство находит свой скоуп статическими методами, которые берут
типовые аргументы семейства: `Scope.select<App, AppDependencies, AppState, V>(context, selector)`
и четыре его соседа. Если писать их обёртками на скоупе, тройка повторяется по
пять раз на скоуп.

У каждого семейства есть и объект-аксессор, который берёт эти аргументы один
раз:

```dart
final class App extends Scope<App, AppDependencies, AppState> {
  static const access = ScopeAccess<App, AppDependencies, AppState>();
}

final counter = App.access.select(context, (state) => state.counter);
```

Это переадресация и ничего больше — каждый метод есть статический метод того же
имени, — так что одно заменяемо другим, а скоуп, которому нужны аксессоры под
своими именами, по-прежнему пишет их сам. Таблица всех восьми — в `README`
пакета.

Остаётся набрать скелет класса, и он тоже едет с пакетом:
`ide/scopo.code-snippets` для VS Code (а также Cursor, Windsurf, Antigravity) и
`ide/scopo-live-templates.xml` для IntelliJ и Android Studio — оба в каталоге
пакета, рядом с `lib/`. Девять шаблонов: по одному на семейство, один на
контейнер зависимостей, один на строку аксессора:

```json
"scopo: The accessor object": {
  "scope": "dart",
  "prefix": "scopo-access",
  "body": ["static const access = ScopeAccess<${1:Widget}>();$0"]
}
```

Куда какой файл класть, написано в `ide/README.md`. Скелеты, которые эти
шаблоны вставляют, компилируются гейтом пакета; сами live templates ничем не
запускаются, так что доказывает их только импорт.
