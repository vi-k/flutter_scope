# AsyncDataScope

> Перевод `doc/async_data_scope.md` (blob `01fd79372fdbe6fabebf20894cda94c0f6c0d28f`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

`AsyncScope`, который производит значение. Инициализация заканчивается объектом,
который она построила, поддерево читает его из скоупа, а утилизация получает его
обратно. Всё остальное — состояния, порядок разбора, `scopeKey`, ожидание
дочерних скоупов — это тема `AsyncScope`, а здесь только то, что меняет
значение.

Берите его, когда скоуп существует *ради* объекта: дескриптор базы данных,
сокет, разобранный файл. Когда объекты уже доступны и важен лишь их жизненный
цикл, `AsyncScope` на один параметр типа легче; когда объектов несколько, у них
порядок и у каждого свой разбор, — контейнер зависимостей описан в теме `Scope`.

```dart
AsyncDataScope<Database>(
  initData: (context) async* {
    yield AsyncDataScopeProgress('opening the database');

    yield AsyncDataScopeReady(await Database.open());
  },
  disposeData: (database) => database.close(),
  progressBuilder: (context, progress) => Text('$progress'),
  errorBuilder: (context, error, stackTrace, progress) => Text('$error'),
  builder: (context, database) => DatabaseView(database: database),
);
```

`AsyncDataScopeBase` — форма для наследования, с `initData`, `disposeData`,
`onMount`, `onUnmount` и четырьмя билдерами в виде переопределений.

## Значение в каждом месте

```dart
AsyncDataScopeReady(await Database.open())
```

— вот где значение входит. Элемент сохраняет его в момент применения готового
состояния, и с этой минуты:

- **`builder`** получает его вторым аргументом — готовой ветке никогда не нужно
  проверять на `null`;
- **`disposeData`** тоже его получает и выполняется, только если инициализация
  удалась, так что аргумент всегда существует;
- **`onUnmount`** получает вместо этого `T?`: он срабатывает в момент ухода скоупа
  с дерева, а это может случиться задолго до того, как значение появилось, или
  после провала;
- **потомки** читают его из контекста (ниже).

Сторона прогресса намеренно типизирована слабо: `AsyncDataScopeProgress` несёт
`Object?`, и билдеры получают его как `Object?`. Параметр типа существует ради
строящегося значения; прогресс — это подпись.

### Значение, которое не доехало, освобождать некому

`AsyncDataScopeReady` — это передача, и до неё значение принадлежит одной лишь
инициализации. Скоуп его не видел, а значит и освободить не может: `disposeData`
выполняется, только если инициализация удалась, а `onUnmount` получает `null`.

Из-за этого версия ловушки, специфичная для этого семейства, особенно
соблазнительна: значение существует, лежит в локальной переменной и выглядит
так, будто за ним уже присматривает скоуп:

```dart
// Неправильно: база открыта, и с ней `disposeData` никогда не позовут.
initData: (context) async* {
  final database = await Database.open();

  yield AsyncDataScopeProgress('migrating');
  await database.migrate();             // бросает

  yield AsyncDataScopeReady(database);
},
disposeData: (database) => database.close(),
```

```dart
// Правильно: не передал — значит закрывать самому.
initData: (context) async* {
  final database = await Database.open();
  var handedOver = false;

  try {
    yield AsyncDataScopeProgress('migrating');
    await database.migrate();

    yield AsyncDataScopeReady(database);
    handedOver = true;
  } finally {
    if (!handedOver) {
      await database.close();
    }
  }
},
disposeData: (database) => database.close(),
```

`finally`, а не `catch`: упавший шаг — только один из двух способов закончить
эту инициализацию досрочно. Второй — отмена: скоуп убрали из дерева или закрыли
через `close()`, так и не дав ему стать готовым, — и она не бросает ничего,
поэтому до `catch` дело не доходит. Разбор целиком — в теме `AsyncScope`; здесь
ловушка хуже, потому что `yield` внутри защиты сам по себе точка, на которой
отмена может закончить тело.

Два способа не писать защиту вовсе: строить значение одним шагом, который не
может упасть на середине, — или взять контейнер зависимостей семейства `Scope`,
который ведёт ровно этот учёт для целого дерева ресурсов. А если значение — это
объект со своим жизненным циклом, а не простой ресурс, то `AsyncControllerScope`
утилизирует его на любом пути, включая тот, где его `init()` бросил.

### Почему значение отдают билдеру, а модель `ScopeModel` — нет

`ScopeModel.builder` получает только контекст, а виджеты под ним берут модель
через `of` или `select`. Это не недосмотр ни там, ни здесь: разница следует из
того, чем являются два объекта.

Модель живёт столько же, сколько скоуп, и всё это время меняется, поэтому важно
именно **когда** её читают: виджет, прочитавший её через `select`, подписан на
прочитанную часть и перестраивается, когда та меняется. Отдать модель билдеру
значило бы вручить неподписанную ссылку и подтолкнуть читать объект целиком там,
где хватило бы селектора.

Значение здесь создаётся один раз, в `initData`, и больше не подменяется.
Подписываться не на что и пропустить нечего, а ветка, где оно вообще существует,
ровно одна — готовая, её и строит `builder`. Передача — это то, что избавляет
эту ветку от `data!` и `isInitialized`, и по той же причине его получают
`dispose(data)` и `unmount(T? data)`.

## Чтение из поддерева

```dart
final database = AsyncDataScope.of<Database>(context, listen: false).data;
```

`of`, `maybeOf` и `select` возвращают `AsyncDataScopeContext`, который добавляет
три члена ко всему, что есть у `AsyncScopeContext`:

| член | до появления значения | после |
| --- | --- | --- |
| `data` | бросает `StateError('Not initialized')` | значение |
| `dataOrNull` | `null` | значение |
| `hasData` | `false` | `true` |

Виджет внутри `builder` по определению находится под готовым скоупом и может
пользоваться `data`. Виджет, который может строиться и во время инициализации —
в `progressBuilder` или добравшийся сюда из другого места дерева, — должен брать
`dataOrNull` или сперва проверять `hasData`.

Для нullable-`T` — `AsyncDataScope<Session?>` — `dataOrNull` на этот вопрос не
отвечает вовсе: он `null` по обе стороны от момента, когда значение появилось,
ведь `null` инициализация вправе выдать и сама. Разницу показывает `hasData`, а
`data` спрашивает о том же с другой стороны: бросает, пока значения нет, и
возвращает тот самый `null`, когда оно есть. Та же двусмысленность доезжает до
`onUnmount`: ему передают `T?`, и сам по себе он одно от другого не
отличит.

«До появления значения» — чуть раньше, чем `isInitialized`. Значение
перехватывают на пролёте, а состояние скоупа применяют в конце кадра или после
всей `pauseAfterInitialization`, которая нарочно длиннее. В этом окне скоуп ещё
строит `progressBuilder`, а `data` уже отвечает — и именно в этом окне идёт разбор
скоупа, ушедшего раньше времени, поэтому `disposeData` и можно обещать значение.

`select` — дешёвый вход, когда важна лишь часть значения:

```dart
final name = AsyncDataScope.select<Profile, String>(
  context,
  (scope) => scope.data.name,
);
```

Параметры типа читаются так же, как везде в пакете: сначала тип самого скоупа,
последним — выбираемый. Селектор получает контекст, а не данные, так что из него
доступны и `dataOrNull`, и `hasError`.

## Чего значение не делает

То, что значение хранится, не делает его наблюдаемым. `AsyncDataScope`
уведомляет своих зависимых при изменении **состояния** — ожидание, прогресс,
готовность, ошибка, — а не когда что-то изменилось внутри значения. База данных,
в которой прибавилось строк, не уведомляет никого.

Это тот же размен, что и у `ScopeModel`, и выходы те же: сделать значение
`Listenable` и поставить под этим скоупом `ScopeNotifier` — либо отдать из него
поток и дать подписаться тем виджетам, которым это нужно.

## В отладчике

Элемент добавляет значение в свою диагностику, поэтому инспектор виджетов и
`debugDumpApp()` показывают рядом со скоупом `data: Database(…)` — и `null`,
пока инициализация не удалась. Два этих состояния легко различить, когда
поддерево выглядит не так, как ожидалось.
