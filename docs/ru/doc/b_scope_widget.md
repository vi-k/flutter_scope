# ScopeWidget

> Перевод `doc/b_scope_widget.md` (blob `19a71a461ddbbbce6288fc9a5889bdf1879b138a`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

Под этим именем живут две вещи. `ScopeWidgetBase` — простейший скоуп пакета,
годный к употреблению как есть: виджет, отдающий поддереву собственные
параметры. `ScopeWidgetCore` и `ScopeWidgetElementBase` — пара, от которой
наследуется любое другое семейство: место, где хранятся подписки, где
`notifyDependents` решает не перестраивать поддерево и где скоуп цепляется за
жизненный цикл элемента.

Первый раздел — чтобы пользоваться семейством. Остальные — когда пишете свой
скоуп или когда скоуп перестроил больше (или меньше), чем вы ожидали.

## ScopeWidgetBase

Параметры виджета и так неизменяемые данные, которые дал предок;
`ScopeWidgetBase` превращает их в скоуп, чтобы потомки могли подписываться на
один параметр, а не перестраиваться на каждое изменение виджета.

```dart
final class ApiConfig extends ScopeWidgetBase<ApiConfig> {
  final String apiKey;
  final Uri baseUrl;

  const ApiConfig({
    super.key,
    super.tag,
    required this.apiKey,
    required this.baseUrl,
    required super.child,
  });

  static String apiKeyOf(BuildContext context) =>
      ScopeWidgetBase.select<ApiConfig, String>(
        context,
        (widget) => widget.apiKey,
      );

  @override
  Widget build(BuildContext context) => child;
}
```

`build` — это то, что скоуп показывает; ту же роль у остальных семейств играет
`buildChild()`. Вернуть `child`, принятый конструктором, — обычная форма, и
поэтому `child` здесь объявлен `required`: базовый класс разрешает его не
задавать, но скоуп, который ничего не показывает, нужен редко.

Три аксессора достаются от базового класса, и все возвращают виджет:

```dart
ScopeWidgetBase.of<ApiConfig>(context, listen: false);      // ApiConfig
ScopeWidgetBase.maybeOf<ApiConfig>(context, listen: false);  // ApiConfig?
ScopeWidgetBase.select<ApiConfig, String>(context, (w) => w.apiKey);
```

Переоткрыть их именованными статиками, как `apiKeyOf` выше, стоит этих трёх
строк: место вызова перестаёт повторять параметры типов, а скоуп сам решает, что
его поддереву позволено читать.

Откуда берутся значения — дело родителя. Когда родитель перестроит `ApiConfig` с
другим `apiKey`, зависимые, выбравшие `apiKey`, будут перестроены, а выбравшие
`baseUrl` — нет; фильтрация описана в теме `base`.

Об одной ловушке стоит сказать прямо: `context`, который получает `build`, — это
собственный элемент скоупа. Поиск из него находит этот самый скоуп, поэтому
`ApiConfig.apiKeyOf(context)` внутри `build` подписывает скоуп на самого себя, а
уведомление о себе перестраивает всё поддерево, а не зависимого. Читайте
параметры напрямую: `apiKey` — поле, а `build` — метод того же объекта.

## Пара, стоящая за каждым семейством

```dart
final class MyScope extends ScopeWidgetCore<MyScope, MyScopeElement> {
  const MyScope({super.key, super.tag});

  @override
  MyScopeElement createScopeElement() => MyScopeElement(this);
}

final class MyScopeElement
    extends ScopeWidgetElementBase<MyScope, MyScopeElement> {
  MyScopeElement(super.widget);

  @override
  void init() {
    // Acquire whatever the scope owns…
    super.init();
  }

  @override
  void dispose() {
    super.dispose();
    // …and release it here.
  }

  @override
  Widget buildChild() => const SizedBox.shrink();
}
```

Оба хука помечены `@mustCallSuper`, и порядок выше — тот, которого держатся
семейства самого пакета: захватывать до `super.init()`, освобождать после
`super.dispose()`. Половины зеркальны, поэтому то, чем владеет слой, живёт
дольше всего, что настроили слои под ним.

Вот и весь контракт: виджет, который умеет создать свой элемент, и элемент,
который знает, что строить. `ScopeWidgetBase` — ровно это, только `buildChild()`
у него делегирует в `build` виджета. Всё остальное, что предлагает пакет —
модель, notifier, асинхронная инициализация, контейнер зависимостей, —
надстроено над теми же двумя классами.

`updateShouldNotify` всегда возвращает `true`, и это звучит расточительно, но не
является таковым: это лишь просьба к элементу уведомить своих зависимых, а
каждого зависимого потом отфильтруют его собственные селекторы. Скоуп никак не
может знать, что важно его потомкам, поэтому решение остаётся за ними.

## notifyDependents

`notifyDependents()` сообщает подписанным потомкам, что что-то изменилось, **не
перестраивая поддерево**. Именно это делает скоуп посильным для часто меняющихся
значений:

```dart
@override
void init() {
  model.addListener(notifyDependents);
  super.init();
}
```

Это `ScopeNotifier` целиком: каждый `notifyListeners()` модели становится
уведомлением, и перестраивают только те виджеты, у которых действительно
изменилось выбранное значение. Состояние `Scope` или `LiteScope` зовёт этот же
метод руками после того, как себя изменило.

Механизм стоит знать, потому что он объясняет ограничения. Зависимого
уведомляют через `didChangeDependencies`, а тот может выполняться только во
время сборки кадра. Поэтому элемент помечает себя грязным, а на получившемся
перестроении уведомляет клиентов и пропускает обновление ребёнка — поддерево
сохраняет свои элементы, состояния и позиции прокрутки нетронутыми.

## Когда поддерево всё-таки перестраивают

Три случая отменяют режим «только уведомить», и каждый сознателен.

**Родитель обновил виджет скоупа.** Новый виджет может означать новые параметры
и другой `buildChild()`, поэтому поддерево перестраивают, даже если уже было
запланировано перестроение-уведомление.

**Скоуп объявил `autoSelfDependence`.** Элемент, который перестраивает
собственное поддерево по мере продвижения своего состояния, не может
пользоваться срезкой: его `buildChild` каждый раз возвращает другую ветку.
`AsyncScope` ставит этот флаг навсегда. `LiteScope` точнее: он начинает с
включённым флагом, пока ветки ожидания, инициализации и ошибки сменяют друг
друга, и сбрасывает его в `buildOnReady()` — с момента, когда на экране готовая
ветка, уведомления перестают перестраивать поддерево.

**Сработала зависимость от себя.** Элемент может подписаться на собственный
скоуп; `InheritedElement` отказывается это записывать (ассерт в
`notifyClients`), поэтому такие подписки хранятся отдельным списком и
уведомляются раньше остальных. Когда одна из них меняется, поддерево
перестраивают — элемент, выбравший значение, и есть элемент, который строит
поддерево.

## Имена в журнале

`toStringShort` виджета скоупа — это `MyScope(#4e0b7)` или `MyScope(cart)`, если
задан `tag`; элемент печатает свой тип и хеш. Логгер скоупа берёт имя из
первого, поэтому `tag` — самый дешёвый способ различить в выводе два скоупа
одного типа. Формат — в теме `debug`.
