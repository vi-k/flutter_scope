# Почему release-запуск не возвращает управление после закрытия окна

> **Состояние на 2026-08-14:** расследование закончено, дефекта в scopo нет,
> код пакета и демо не менялся. Пункт удалён из бэклога; для ручной проверки
> release-сборки записан рабочий способ запуска без `flutter run`.
> **Что это:** разбор зависания IDE после закрытия `example/scopo_demo`,
> запущенного на macOS в release-режиме.
> **Связанные записи:** нет.

## Что воспроизведено

На закреплённом Flutter 3.29.0 команда

```sh
fvm flutter run -d macos --release
```

успешно собрала и запустила `scopo_demo`. Перед закрытием окна цепочка
процессов содержала `rtk`, FVM, `flutter_tools.snapshot` и исполняемый файл
`scopo_demo.app/Contents/MacOS/scopo_demo`.

После закрытия окна процесс `scopo_demo` исчез, но
`flutter_tools.snapshot run -d macos --release` остался жив. За следующие
пять секунд он ничего не вывел и не вернул управление. Нажатие `q` в его
терминале сразу завершило команду с кодом 0 и строкой `Application finished.`

Это отделяет два события, которые снаружи выглядели одним зависанием:

- release-приложение штатно завершилось;
- резидентный процесс Flutter CLI не заметил завершение приложения.

`AppDelegate.swift` у демо явно возвращает `true` из
`applicationShouldTerminateAfterLastWindowClosed`, поэтому исчезновение
последнего окна должно завершать приложение и в этом прогоне действительно
его завершило. Утилизация скоупов не удерживала процесс.

## Причина в Flutter CLI

Путь release-запуска в Flutter 3.29.0 устроен так:

1. `DesktopDevice.startApp` запускает исполняемый файл через `Process` и
   подписывается на `process.exitCode` только для удаления процесса из
   внутреннего множества `_runningProcesses`.
2. Для release-сборки тот же метод сразу возвращает успешный `LaunchResult`:
   VM Service в этом режиме нет.
3. `ColdRunner` при обычном resident-запуске ждёт `waitForAppToFinish()`.
4. В debug/profile завершение VM Service доводит runner до завершения. В
   release такого сигнала нет, а завершение stdout/stderr в
   `DesktopLogReader` лишь закрывает поток логов: подписка из
   `startEchoingDeviceLog` не задаёт обработчик `onDone`, который мог бы
   завершить runner.

Поэтому `flutter run` знает, что дочерний процесс завершился, но не связывает
это событие с `appFinished()`. Это поведение Flutter tools, а не приложения.
Сравнение с установленными локально Flutter 3.44.4 и stable показало тот же
путь в `desktop_device.dart`; простое переключение на один из этих SDK не
устраняет механизм проблемы.

## Проверенные обходы

Скрытый флаг `--no-resident` не подходит для ручного запуска desktop-release:

```sh
fvm flutter run -d macos --release --no-resident --no-build
```

Команда завершилась с кодом 0, но после неё не осталось и процесса
приложения. Кроме того, в этом прогоне Flutter всё равно выполнил сборку,
несмотря на `--no-build`.

Рабочий способ — разделить сборку и запуск:

```sh
cd example/scopo_demo
fvm flutter build macos --release
open build/macos/Build/Products/Release/scopo_demo.app
```

Прямой запуск проверен: после возврата `open` жил только процесс
`scopo_demo`, без отдельного `flutter run`. После завершения приложения
удерживать IDE или терминал нечему. Для разработки остаются debug/profile,
где VM Service корректно сообщает Flutter CLI о завершении.

## Что не делалось

Flutter SDK не патчился, код scopo и example не менялся. Минимальный внешний
репродуктор и issue в `flutter/flutter` не создавались: для задачи проекта
достаточно установить владельца дефекта и зафиксировать рабочий обход.
