## Общая оценка

Пакет технически готов и держит планку, которой у большинства пакетов такого
размера нет. **160 из 160 pub points** — анализатору придраться не к чему.
Одиннадцать тем на 3188 строк объясняют то, чего не даёт справочник API:
порядок событий, размены, ловушки. Три примера, один из которых — шесть уроков
по навигации. Под этим 453 теста с включённым leak-трекером и mutation score
≈83 %, полученный не оценкой, а 94 прицельными мутациями.

И у пакета есть настоящая причина существовать: **упорядоченный разбор**. Скоуп
дожидается своих детей, `scopeKey` заставляет пересозданный скоуп подождать
предыдущий, отмена недоделанной инициализации возвращает уже взятое. Ни
provider, ни riverpod этого не дают — они решают задачу доставки значения по
дереву, а не задачу владения им во времени.

**Проблема ровно одна, и она не в коде: этого никто не узнает.** Все семь
находок ниже — про расстояние между тем, что пакет умеет, и тем, что человек
успевает понять за первые пять минут. Пакет написан так, будто читатель уже
решил его взять; на деле в первые минуты он решает, стоит ли.

## Как проводилось

Не чтением `lib/`, а прохождением пути потребителя, в его порядке:

| шаг | чем смотрел |
| --- | --- |
| страница пакета | `pub.dev/packages/scopo`, отрендеренный README, score API |
| README | целиком, 652 строки, в порядке чтения сверху вниз |
| первый пример | `example/minimal/lib/main.dart` |
| поверхность API | `dart doc` локально, подсчёт типов по сгенерированным страницам |
| темы | список, объёмы, наличие ответов на вопросы новичка |
| поиск ответов | грепы по README и всем одиннадцати темам |

Числа в находках — измеренные, не оценочные: счётчики строк, счётчик типов из
сгенерированной документации, счётчики вхождений по грепу.

## U1. Нигде не сказано, зачем это вместо provider или riverpod

На 652 строки README и 3188 строк тем — **ноль упоминаний любой альтернативы**.
Грепы по `provider`, `riverpod`, `get_it`, `InheritedWidget` дают два
совпадения, и оба — случайные слова в другом контексте.

Это первый вопрос человека, открывшего страницу пакета, и единственный, от
которого зависит, будет ли второй. Причина, по которой scopo стоит брать —
владение во времени, а не доставка по дереву, — читателю нигде не предъявлена:
её приходится выводить самому из списка Features, где она разложена на четыре
пункта, каждый из которых по отдельности выглядит как деталь реализации
(«Ordered disposal», «Async initialization»).

Раздел Features отвечает на вопрос «что умеет». Не отвечает никто на вопрос
«вместо чего».


**Вердикт: исправлено.** 2026-08-23, тем же коммитом, что и эта запись. Раздел
«Why another one» стоит сразу после вводного абзаца, до Features, — то есть
там, где вопрос и возникает. Он говорит одно: те пакеты отвечают за доставку
значения, scopo — за владение им во времени, и это стоит отдельного пакета
только тогда, когда у объектов есть собственный жизненный цикл. Заканчивается
раздел абзацем «когда scopo брать не стоит» — без него текст читался бы как
реклама.

**Утверждения о чужих пакетах проверены, а не написаны по памяти.** Через
документацию riverpod: `ref.onDispose` принимает синхронный колбэк, а
`ProviderContainer.dispose()` возвращает `void`, — значит «дождаться
асинхронной уборки» там негде выразить, и это ровно та разница, ради которой
раздел писался. Признано и обратное: `FutureProvider` и `AsyncValue` дают
ветки загрузки и ошибки, то есть часть обещаний scopo riverpod закрывает.
Несправедливое сравнение здесь было бы хуже отсутствующего: знающий читатель
поймает неточность и перестанет верить остальному.

Порядок разделов: `Scope` (три части — контейнер зависимостей, состояние,

разобраться, зачем инициализация — это `Stream`.

Заголовок усугубляет: «специализированные» читается как «на потом», хотя
`ScopeModel`, `ScopeNotifier` и `ScopeWidgetBase` — ровно то, чем человек
начнёт пользоваться в первый день.


**Вердикт: исправлено.** 2026-08-23, тем же коммитом, что и эта запись. README
переставлен в порядок тем из `dartdoc_options.yaml` — от меньшего семейства к
большему: `ScopeWidgetBase`, `ScopeModel`, `ScopeNotifier`, `AsyncScope`,

## U3. Публичных типов сто два

Считано по сгенерированной документации: **99 классов и 3 миксина**. У provider
их около двадцати.

Для первого экрана нужно примерно пятнадцать: `Scope`, `ScopeState`,
`ScopeDependencies`, `ScopeInitState` с тремя наследниками, `AsyncScope`,
`ScopeModel`, `ScopeNotifier`, `LiteScope`, `ScopeConfig`, `ScopeObserver`.
Остальные восемьдесят с лишним — это базы для расширения (`*Core`, `*Base`,
`*ElementBase`, по три-четыре на каждое из восьми семейств) и прямые
внутренности: `ScopeInheritedElement`, `ScopeInheritedWidget`,
`ScopeModelInheritedElement`.

В IDE это выглядит так: набираешь `Scope` — получаешь два десятка вариантов без
единой подсказки, какой из них твой. Барель честно перечисляет имена вместо
`hide` (и это правильное решение, принятое волной 24), но перечисляет их **в
одном списке**, где `Scope` стоит рядом с `ScopeInheritedElement`.

Разделение на два бареля — `scopo.dart` для потребителя и отдельный для тех,
кто расширяет, — снимает это целиком. Правка ломающая: до публикации стоила бы
ноль, теперь — мажорную версию.

**Вердикт: отложено владельцем 2026-08-23; находка верна в симптоме и неверна
в лекарстве.** Сто два типа — факт, и он измерен заново. Но обещание «разделение
на два бареля снимает это целиком» проверку не прошло, и вот чем:

- **откуда берутся сто два.** По месту объявления: `lib/src/scope/` — **84**,
  `lib/src/utils/` — 12, `lib/src/environment/` — 6. То есть поверхность
  порождена не базовыми классами, а тем, что семейств восемь и у каждого свой
  виджет, `Base`, `Core`, `ElementBase`, `Context` и `State`;
- **разделение уносит 23 из 102.** Во второй барель по суффиксам уходят
  `*Core`, `*CoreState`, `*ElementBase`, `Inherited*`, плюс `AsyncScopeParent` и
  `AsyncScopeModel`. В основном остаётся **79**, и автодополнение по `Scope`
  остаётся стеной. Вынести заодно утилиты — ещё 12, то есть 67; всё равно не
  «целиком»;
- **`*Core` и `*ElementBase` не мертвы снаружи, вопреки ожиданию.**
  `AsyncScopeCore`, `AsyncScopeElementBase`, `ScopeModelCore`,
  `ScopeModelElementBase`, `ScopeWidgetCore`, `ScopeWidgetElementBase`,
  `ScopeNotifierCore`, `ScopeNotifierElementBase` встречаются в примерах
  пакета — на них написана демка. Значит это не «спрятать», а «переложить», и
  ломающее для всех, кто расширяет;
- **зато шестнадцать имён не встречаются нигде снаружи** — ни в трёх примерах,
  ни в README, ни в одиннадцати темах: `AsyncControllerScopeElementBase`,
  `AsyncDataScopeCore`, `AsyncDataScopeElementBase`, `AsyncScopeModel`,
  `ListenableSubscription`, `LiteScopeCore`, `LiteScopeCoreState`,
  `LiteScopeElementBase`, `ScopeCore`, `ScopeCoreState`,
  `ScopeDependencyAnyCancelled`, `ScopeDependencyAnyFailed`,
  `ScopeDependencyAnySuccess`, `ScopeDependencyMixin`, `ScopeElementBase`,
  `ScopeModelInheritedElement`. Часть из них наверняка обязана быть публичной,
  потому что стоит в сигнатурах, — это не проверено по коду. **Здесь и лежит
  настоящее сокращение поверхности, а не в перекладывании между барелями.**

Владельцу предложены четыре пути: сначала сократить и потом делить; только
разделить; разделить с утилитами третьим барелем; отложить. **Выбрано
отложить** — мажорная версия того не стоит, пока нет жалоб от реальных
потребителей. Измерение записано здесь, чтобы следующий заход начинался с
проверки шестнадцати имён по сигнатурам, а не с повторного пересчёта.

## U4. Аксессоры пишутся руками, и это самая заметная эргономическая цена

В `example/minimal` на один скоуп приходится **четыре статических обёртки**, и
каждая повторяет типы:

```dart
static V select<V>(BuildContext context, V Function(AppState state) selector) =>
    Scope.select<App, AppDependencies, AppState, V>(context, selector);
```

Тип приложения назван в объявлении класса, ещё трижды в параметрах базового
класса и ещё раз в каждом вызове. И так в каждом скоупе приложения — а скоупов
в приложении, ради которого пакет и пишется, десятки.

Обойти это в Dart нечем: статические члены не наследуются, поэтому базовым
классом обёртки не убрать. Остаются кодогенерация (зависимость от
`build_runner` и целый слой, которого у пакета сейчас нет) либо другая форма
доступа — например, один константный объект-аксессор на скоуп вместо четырёх
методов. И то и другое — решение владельца, а не работа по списку.

Находка не о том, что это сделано неправильно, а о том, что **это первое, обо
что читатель спотыкается в примере**, и в README про цену не сказано.

**Вердикт: исправлено, обоими путями сразу.** 2026-08-23, версия 0.11.0;
**шаблоны дорабатывались 2026-08-24 десятком заходов по замечаниям владельца, и
итог отличается от описанного ниже** — их одиннадцать, скелеты пишут статики
скоупа, а не `ScopeAccess`, у `scopo-data` и `scopo-controller` нет `select`.
Что именно и почему изменилось — в `docs/handoff.md`, «Что дальше», п. 15;
проза этого вердикта оставлена как написана.
Владелец выбрал оба варианта — объект-аксессор в пакете и шаблоны редакторов, —
и второй предложил сам. Что стоит унести дальше:

- **у каждого из восьми семейств теперь свой аксессор** (`ScopeAccess`,
  `LiteScopeAccess`, `ScopeWidgetAccess`, `ScopeModelAccess`,
  `ScopeNotifierAccess`, `AsyncScopeAccess`, `AsyncDataScopeAccess`,
  `AsyncControllerScopeAccess`): он берёт типовые аргументы один раз и
  переадресует статикам того же имени. Пятнадцать строк обёрток на скоуп
  становятся одной. Правка **не ломающая** — статики остались, и скоуп, которому
  нужны свои имена, пишет их как писал;
- **типы выводятся на месте вызова, и это проверено анализатором, а не глазом:**
  на пробе он сам сказал, что аннотации `int`/`String`/`AppState` избыточны;
- **тест сравнивает аксессор со статиком, а не с ожидаемым значением.** Тест на
  значение прошёл бы для аксессора, подключённого не к тому статику, если типы
  совпали; сравнение с самим статиком — нет;
- **большинство мутаций здесь ловит компилятор, и одна не ловилась ничем.**
  Подмена статика не проходит по типам, а вот `listen: listen` → `listen: true`
  компилируется и сьютой не ловилась. Закрыто тестом со счётчиком сборок у
  `const`-читателя — того самого приёма, который волна 14 вывела для P2-13;
- **сниппеты — это код, и его надо компилировать.** Проверка нашла два неверных
  скелета сразу: у `ScopeModelBase` и `ScopeNotifierBase` `create` и `dispose` —
  поля конструктора, а не переопределяемые методы, и я написал их по догадке.
  Теперь скелеты разворачиваются в `test/ide/snippet_skeletons.dart`, который
  анализирует гейт;
- **проверка обязана воспроизводить то, что вставит редактор.** Первая версия
  компилировала `Text('\$error')` — с экранированием формата VS Code, — а
  редактор вставляет `Text('$error')`. Пока экранирование не сняли, проверялся
  не тот код;
- **у IntelliJ литеральный доллар пишется `$$`, а не `\$`.** Генератор сначала
  перенёс экранирование VS Code как есть: получался валидный Dart, печатающий
  слово «$error» вместо значения. Держится тестом;
- **контекстов у плагина Dart ровно два** — `DART` и `DART_STATEMENT`, — и это
  взято из `plugin.xml` установленной Android Studio, а не из памяти. Шаблоны
  объявляют классы и члены, поэтому у них `DART`;
- **чего проверить не удалось:** принимает ли IntelliJ сам файл. XML корректен и
  повторяет формат встроенных шаблонов плагина, но подтверждает это только
  импорт. Сказано и в `ide/README.md`, и в теме — обещание не выдаётся за
  проверенное.

## U6. В README ни слова про тестирование

Грепы по README не дают ничего: как тестировать приложение со скоупами, что
делать с `ScopeConfig` между тестами, почему разбор асинхронный и `pumpAndSettle`

В теме `debug` это есть, и написано хорошо. Но вопрос возникает у каждого, кто
дошёл до второго дня работы с пакетом, а README — то, что читают первым и часто
единственным. Пакет, обещающий детерминированный разбор, обязан сказать, как
этот разбор увидеть в тесте.


**Вердикт: исправлено.** 2026-08-23, тем же коммитом. Раздел «Testing» стоит
после «Observing and configuration» — там, где уже введены наблюдатель и

спотыкаются до первого зелёного теста: `ScopeConfig.reset()` не сбрасывает

`pumpAndSettle` двигает фейковые часы и асинхронного разбора не дожидается.
Последнее сверено с темой `debug`, чтобы README не обещал иного: четыре
таймаута нарочно меряются по реальному времени.

## U7. `NavigationNode` — самостоятельная библиотека внутри пакета про скоупы

Проверено: **внутри `lib/` `NavigationNode` не используется ничем**, и сам он от
скоупов не зависит (семь упоминаний `Scope` — в дартдоке). Это 26 КБ кода, свой
раздел README, свой пример из шести уроков и заметная доля находок четвёртого
ревью.

Тому, кому нужен DI, он едет в архиве без нужды. Тому, кто ищет решение для
вложенной навигации и системной кнопки «назад», его не найти: он лежит в пакете,
чьи описание и топики говорят про scope, state-management и dependency
