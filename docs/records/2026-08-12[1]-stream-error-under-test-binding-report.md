# Почему `Stream.error` не доходит до модели под тестовым биндингом

> **Состояние на 2026-08-12:** расследование закончено, дефекта в scopo нет,
> код не менялся. Добавлен тест на непокрытую ветку ошибки
> (`test/async_scope_test.dart`), пункт из «Известных проблем» в
> `docs/handoff.md` переформулирован в предупреждение для авторов тестов.
> **Что это:** разбор пункта, висевшего с 2026-07-30: «`Stream.error(...)` как
> init-стрим не доходит до модели под `AutomatedTestWidgetsFlutterBinding`,
> в plain `test()` работает — возможно, скрывает проблему планирования в
> `_performAsyncInit`».
> **Связанные записи:** `2026-07-30[2]-audit-fixes-log.md` (там пункт
> заведён, Task 8).

## Что воспроизведено

`AsyncScope`, у которого `init` возвращает `Stream.error(...)`, под
`testWidgets` остаётся в `AsyncScopeWaiting` навсегда: ни `pump()`, ни
`pump(Duration(seconds: 1))`, ни `idle()`, ни четыре `pump()` подряд не
переводят его в `AsyncScopeError`. Ветка ошибки не строится, исключений
`tester.takeException()` не видит.

## Где теряется

Дело не в scopo: то же самое воспроизводится на голом `dart:async`, без
пакета. Четыре комбинации в одном прогоне под `testWidgets`, одна `pump()`:

| Поток | Ошибка доставлена |
| --- | --- |
| `Stream.error(...)` → `listen` | да |
| `Stream.error(...)` → `asyncMap` → `listen` | **нет** |
| `StreamController` c `addError` до подписки → `asyncMap` → `listen` | **нет** |
| `async*` с `throw` → `asyncMap` → `listen` | да |

Условие потери — сочетание двух вещей: ошибка **уже лежит в буфере потока к
моменту подписки** и поток пропущен через **`asyncMap`**. Ошибка, возникшая
после подписки (обычный `async*`), проходит через тот же `asyncMap`
нормально — поэтому все существующие тесты ветки ошибки работают.

Ограничение принадлежит фейковому времени тестового биндинга: внутри
`tester.runAsync(...)`, где код исполняется в настоящей зоне, ошибка
доставляется во всех четырёх комбинациях. В `plain test()` — тоже.

## Что это значит для пакета

`_performAsyncInit` строит подписку как `initAsync().asyncMap(...).listen(...)`,
и в реальном приложении такой `init` работает: доставка подтверждена через
`runAsync`. Менять `asyncMap` не на что — он и выполняет асинхронную обработку
состояний инициализации. Гипотеза из исходного пункта («скрывает проблему
планирования в `_performAsyncInit`») не подтвердилась.

Правило для тестов: ветку ошибки инициализации поднимать `async*`-потоком,
который бросает после первого события, а не `Stream.error(...)`. Если
`Stream.error` нужен именно как таковой — только внутри `tester.runAsync`.

## Что сделано попутно

Путь «ошибка пришла из потока инициализации» не был покрыт вовсе: существующие
тесты либо бросают синхронно до создания потока (ошибка уходит в зону, минуя
модель), либо бросают уже после `AsyncScopeReady`. Добавлен тест
`an error raised inside the init stream reaches the model with the last
progress, and the error branch is built` — он проверяет и сохранение
последнего прогресса в `AsyncScopeError`. Нагруженность подтверждена: с
`progress: null` вместо чтения текущего состояния тест падает именно на этой
проверке.
