# Волна 1 чистки ревью: очистка доводится до конца

> **Состояние на 2026-08-16:** сделано и смержено в `main` тремя коммитами —
> `26d055e` (P1 №3), `4719ed9` (P2 №5) и коммит этой записи (P2 №4).
> **Что это:** отчёт о первой волне чистки находок полного предвыпускного
> ревью; все три находки об одном — освобождение ресурсов не должно
> прерываться на первой неудаче.
> **Связанные записи:** `2026-08-14[10]-project-review.md` (сами находки),
> `2026-08-14[9]-project-review-plan.md`.

## Что объединяет три находки

Пакет обещает, что всё захваченное будет отдано. Три находки описывали три
разных места, где обещание рвалось на первом же исключении:

- **P1 №3** — зависимость освобождалась, только если её инициализация
  закончилась успехом;
- **P2 №5** — последовательная группа бросала обход утилизации на первом
  отказавшем disposer;
- **P2 №4** — ошибка любого пользовательского хука по дороге наружу уносила с
  собой всю обязательную очистку.

Во всех трёх случаях дефект один: *решение продолжать очистку зависело от того,
как прошёл предыдущий шаг*. Правка везде одна и та же по смыслу — обязательные
этапы исполняются независимо друг от друга, а ошибки отдаются после того, как
всё освобождено.

## P1 №3 — единственный блокер выпуска (`26d055e`)

`_ScopeDependencyImpl.disposalRequired` спрашивал состояние
(`state is ScopeDependencyInitialized`). Инициализатор, который успел взять
ресурс и записать `dep.dispose`, а потом упал или был отменён, оставался в
`Failed`/`Cancelled` — и утилизация его пропускала.

Критерием стало то, **что зависимость держит**:

```dart
bool get disposalRequired => !_isDisposalDone && _helper?.dispose != null;
```

`dispose()` больше не смотрит на состояние вовсе: зарегистрированный disposer
срабатывает ровно один раз при любом исходе, `_helper` очищается в `finally`.

Тесты — `test/scope_dependency_partial_test.dart`, группа «a dependency that
failed after taking something»: синхронный отказ, асинхронный отказ,
«ничего не брал — нечего отдавать», «отдаёт ровно один раз».

**Побочный эффект, который надо знать.** Восемь ожиданий в
`scope_auto_dependencies_test.dart` изменились: зависимость, зарегистрировавшая
disposer и отменённая, теперь после `dependencies.dispose()` сообщает
`disposed`, а не `cancelled`. Это ровно тот случай, о котором ревью и говорило,
и правились только строки снимков **после** вызова утилизации. Мутация старого
критерия роняет 10 тестов.

## P2 №5 — обход утилизации доходит до конца (`4719ed9`)

`_ScopeDependencySequential.dispose()` шёл в обратном порядке и `yield*`-ил
каждую утилизацию. Первый отказ обрывал обход: всё, что ниже, оставалось с
ресурсами, хотя дерево считалось утилизированным. Временная проба на
`[c, b, a]` с отказом `b` дала `['c', 'b']`.

Теперь каждое освобождение под своим `try`, обход доходит до конца, первая
ошибка пробрасывается после него.

**Что стоило времени.** Первая версия правки выглядела рабочей и не работала:

```dart
try {
  yield* dependency.runDispose().map(_path);   // ошибка сюда не приходит
} on Object catch (error, stackTrace) { ... }
```

**Ошибка внутри делегированного потока идёт прямо подписчику**, и никакой
`catch` в генераторе её не видит. Помогает только явный обход:

```dart
await for (final path in dependency.runDispose()) {
  yield _path(path);
}
```

Мутация обратно на `yield*` роняет 1 тест.

## P2 №4 — пользовательский хук не отменяет обязательную очистку

Ревью назвало четыре цепочки; в работе их оказалось пять — к четырём
названным добавился обход детей в группе зависимостей.

### Что было

| место | что уносила ошибка |
| --- | --- |
| `_AsyncScopeElement.unmount` | весь `super.unmount()`: снятие с родителя, `scopeKey`, модель |
| `_AsyncDataScopeElement.unmount` | то же самое |
| `AsyncScopeElementBase._performAsyncDispose` | `disposeAsync()` **и** блок `finally` целиком |
| `ScopeElementBase.unmount` | базовую очистку за `_dependencies.unmount()` |
| `ScopeElementBase.disposeAsync` | утилизацию зависимостей за упавшим состоянием |
| `ScopeDependencyGroup.unmount` | `unmount` всех соседей за первой упавшей зависимостью |

Самая дорогая — третья: `onWaitForChildrenTimeout()` вызывается из
`waitForChildren`, то есть **до** `try/finally`, который отдаёт место у
родителя, `scopeKey` и модель. Ошибка там оставляла скоуп в очереди навсегда:
следующий скоуп на том же ключе вставал за записью, которую некому закрыть.

### Что стало

Обязательные этапы разведены и исполняются независимо. `_performAsyncDispose`
теперь читается как три этапа, каждый под своей защитой:

```dart
AsyncError? failure;

try {
  try {
    await _prepareForDisposal();      // отказ от ожиданий; здесь user code
  } on Object catch (error, stackTrace) { failure = AsyncError(...); }

  try {
    if (_initSucceeded) { await disposeAsync(); }   // и здесь
  } on Object catch (error, stackTrace) { failure ??= AsyncError(...); }
} finally {
  // снять с родителя, выйти из очереди ключа, утилизировать модель
}

if (failure case final failure?) {
  Error.throwWithStackTrace(failure.error, failure.stackTrace);
}
```

Ожидания (отмена ожидания ключа, отмена инициализации, ожидание детей) выделены
в `_prepareForDisposal()` — это дало имя этапу и оставило диff читаемым.

Остальные пять мест — тот же приём в меньшем масштабе: `try/finally` вокруг
пользовательского хука в двух `unmount` семейств и в `ScopeElementBase.unmount`;
в `ScopeElementBase.disposeAsync` ошибка состояния запоминается, зависимости
утилизируются, ошибка отдаётся после; в группе зависимостей `unmount` каждого
ребёнка под своим `try`, первая ошибка — после обхода.

Заодно `unmount` групп поднят в `ScopeDependencyGroup`: последовательная и
параллельная реализации были дословно одинаковы, и правка в двух копиях сразу
разошлась бы.

### Тесты

`test/cleanup_after_user_error_test.dart`, шесть тестов. Утверждения — о
следствиях, не о таймингах: доказательством служит то, что освобождаемый ресурс
вернулся.

| тест | что доказывает |
| --- | --- |
| `AsyncScope disposes of itself after a failing onUnmount` | `disposeAsync` дошёл |
| `AsyncScope releases its scopeKey after a failing onUnmount` | преемник на том же ключе вошёл сразу |
| `AsyncScope disposes of itself after a failing onWaitForChildrenTimeout` | отказались от ожидания, а не от утилизации |
| `AsyncDataScope disposes of itself after a failing onUnmount` | значение освобождено |
| `Scope unmounts and disposes of every dependency after a failing one` | сосед размонтирован, обе зависимости утилизированы |
| `Scope disposes of its dependencies after a failing state disposal` | зависимости отдали своё за упавшим состоянием |

У теста про `scopeKey` собственный предел преемника выставлен в `Duration(days:
1)` — истечение ожидания не может быть тем, что его впустило.

**Мутационная проверка: шесть мутаций, каждая роняет тесты** (2, 1, 1, 1, 1, 1
соответственно).

### Чего пришлось добиваться отдельно

Две ошибки из шести приходят **не** через `tester.takeException()`:
`_performAsyncDispose()` вызывается на отброшенном future, поэтому проброс
превращается в неперехваченную ошибку зоны и мгновенно валит тест. Оба таких
теста обёрнуты в `runZonedGuarded`, как это уже сделано в
`async_scope_coordinator_test.dart` для `onScopeKeyTimeout`.
