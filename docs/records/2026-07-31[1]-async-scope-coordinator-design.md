# Редизайн координации AsyncScope

> **Состояние на 2026-08-12:** реализовано и смержено в `main` (12b4c9f); описанный здесь API — действующий (`AsyncScopeCoordinator`, `KeyedAccessQueues`, `ChildRegistry`). Позднее уточнён исправлениями из `2026-08-01[1]-cross-review-fixes-report.md`, поэтому детали поведения сверяйте с кодом и `docs/architecture.md`.
> **Что это:** спецификация редизайна координации `AsyncScope`: отказ от глобального `asyncScopeRoot` в пользу координатора, владеющего очередями `scopeKey` своего поддерева.
> **Связанные записи:** план реализации — `2026-07-31[2]-async-scope-coordinator-plan.md`.

Дата: 2026-07-31. Целевой релиз: **0.10.0** (ещё не опубликован).

## Проблема

Координация асинхронных скоупов состоит из двух механизмов, и оба сейчас
опираются на глобальное состояние.

1. **Очереди по `scopeKey`.** `_AsyncScopeCoordinatorElement._queues` объявлено
   как `static`, поэтому все экземпляры `AsyncScopeCoordinator` в процессе
   делят одно пространство ключей. Два независимых поддерева — и два теста в
   одном процессе — блокируют друг друга по совпадающему ключу. Виджет
   выглядит как область видимости, но ведёт себя как глобальный синглтон.
2. **Корень ожиданий.** `asyncScopeRoot` — глобальный синглтон, в котором
   копятся скоупы без родителя-скоупа. Он ничем не очищается между тестами и
   не привязан к дереву.

Сопутствующее:

- элемент координатора не переопределяет `dispose()` — следствие того, что
  карта статическая, а не его собственная;
- `_AsyncScopeCoordinatorQueue.close()` не вызывается нигде — мёртвый код;
- таймаут ожидания детей живёт в вызывающем коде (`async_scope_core.dart`),
  а не в `waitForChildren`, и там же стоит `_children.clear()` в `finally`;
- на единственный в пакете примитив синхронизации (FIFO-мьютекс с отменой и
  таймаутом) нет ни одного теста.

Очередь **не течёт**: она сама удаляется из карты, когда из неё вышел
последний участник. Проблема именно в разделяемости, а не в утечке.

## Принятые решения

1. **Координатор — единственный владелец** обоих механизмов: очередей по
   ключам и корня ожиданий. `asyncScopeRoot` удаляется.
2. **Ближайший координатор выигрывает.** Каждый экземпляр — своё пространство
   ключей и свой корень. Одинаковый `scopeKey` под разными координаторами
   друг друга не блокирует.
3. **Всё уезжает в 0.10.0**, чистым удалением, без цикла депрекации:
   релиз не опубликован, а удаляемыми символами не пользуются даже примеры и
   тесты пакета.
4. **Чистое Dart-ядро + тонкий виджетный слой** — чтобы координацию можно
   было покрыть юнит-тестами.

## Архитектура

### Ядро: `lib/src/scope/e_async_scope/scope_coordination.dart`

Самостоятельная библиотека — **не** `part` от `scope.dart` — и она **не**
экспортируется из `lib/scopo.dart`. Тесты импортируют её по пути
`package:scopo/src/scope/e_async_scope/scope_coordination.dart`.

Причина ровно одна: `scope.dart` экспортируется целиком, поэтому внутри него
у класса есть только два состояния — приватный и недоступный тестам, либо
публичный и попадающий в API пакета вместе с dartdoc на pub.dev. Отдельная
библиотека даёт третье: классы обычные, тестам доступны, а в публичную
поверхность не входят, потому что их никто не экспортирует. Плата — одна
библиотека вне общей `part`-архитектуры пакета; решение принято осознанно
(рассматривались также приватные классы без юнит-тестов и публичные с
`@visibleForTesting`).

Ядро не импортирует Flutter, только `dart:async` и `package:meta`.

```dart
/// FIFO-мьютекс по ключам.
class KeyedAccessQueues {
  /// Число живых очередей. Для диагностики и тестов.
  int get length;

  bool containsKey(Object key);

  Future<void> enter(
    Object key,
    AccessEntry entry, {
    Duration? timeout,
    void Function(TimeoutException error, StackTrace stackTrace)? onTimeout,
  });
}

/// Место в очереди по одному ключу.
class AccessEntry {
  AccessEntry(String debugName);

  bool get isCompleted;
  bool get isWaiting;
  bool get isCancelled;

  /// Освобождает ключ. Обязателен для каждой вошедшей записи.
  void exit();

  /// Прерывает ожидание доступа. Запись остаётся в очереди до [exit].
  void cancel();
}

/// Реестр детей одного родителя.
class ChildRegistry {
  bool get hasChildren;
  int get childrenCount;

  ChildEntry registerChild(String debugName);

  Future<void> waitForChildren({
    Duration? timeout,
    void Function(TimeoutException error, StackTrace stackTrace)? onTimeout,
  });
}

class ChildEntry {
  void unregister();
}
```

Семантика, которую надо сохранить в точности (она уже такая):

- `enter` в пустую очередь завершается сразу; иначе запись помечается
  `isWaiting` и ждёт завершения **всех** ранее вошедших записей, либо своей
  отмены, либо своего завершения;
- `cancel` допустим только во время ожидания (`assert(isWaiting)`), прерывает
  ожидание, но **не** выводит запись из очереди — она остаётся до `exit`;
- `exit` завершает запись и удаляет её; опустевшая очередь удаляется из карты;
- `waitForChildren` без детей завершается немедленно;
- по таймауту ядро **не бросает**: зовёт `onTimeout` с готовым
  `TimeoutException` и завершается нормально — политика «сообщить и пропустить
  дальше» остаётся за виджетным слоем;
- `waitForChildren` очищает реестр **только если истёк таймаут**: при успешном
  ожидании он и так пуст, потому что каждый ребёнок удаляет себя сам в
  `unregister`. Сейчас вызывающий код чистит безусловно, но на успешном пути
  это no-op, так что поведение не меняется — только становится осмысленным для
  повторных вызовов (координатор, в отличие от скоупа, живёт долго и его
  `waitForChildren` могут позвать не один раз).

### Виджетный слой (остаётся `part of scope.dart`)

- `_AsyncScopeCoordinatorElement` подмешивает `AsyncScopeParent` и владеет
  `final _queues = KeyedAccessQueues()` — полем экземпляра.
- `AsyncScopeCoordinator.enter(context, key, entry, {timeout, onTimeout})` —
  сигнатура и текст ошибки при отсутствии координатора не меняются.
- Новый статический хелпер
  `AsyncScopeCoordinator.waitForChildren(context, {timeout, onTimeout})` —
  замена того, зачем существовал `asyncScopeRoot`: приложение может дождаться
  верхнеуровневых скоупов. Отдаётся именно статикой, чтобы не публиковать тип
  приватного элемента. При отсутствии координатора в дереве бросает ту же
  `FlutterError`, что и `enter`.
- `AsyncScopeParent` остаётся публичным миксином (он подмешан в публичный
  `AsyncScopeElementBase` и служит маркером для поиска предка), но внутри
  делегирует в `ChildRegistry`.

Поиск родителя в `_registerWithParent` уже написан как «первый предок с
`AsyncScopeParent`», поэтому координатор начинает находиться сам собой, и
`?? asyncScopeRoot` исчезает без иных правок.

### Правки в `async_scope_core.dart`

- `_asyncScopeParentEntry = (parent ?? asyncScopeRoot).registerChild(…)` →
  `parent?.registerChild(…)`; поле уже nullable, снятие регистрации в `finally`
  уже написано через `?.`.
- Блок ожидания детей с ручным `future.timeout(...)`, `try/on TimeoutException`
  и `_children.clear()` схлопывается в один вызов:

```dart
await waitForChildren(
  timeout: waitForChildrenTimeout ?? ScopeConfig.defaultWaitForChildrenTimeout,
  onTimeout: (error, stackTrace) {
    FlutterError.reportError(
      FlutterErrorDetails(exception: error, stack: stackTrace, library: 'scopo'),
    );
    onWaitForChildrenTimeout();
  },
);
```

  Текст `TimeoutException` («couldn't wait for the children to complete: …»)
  формирует ядро, оно же подставляет список незавершённых детей.
- Тип записи меняется с `AsyncScopeCoordinatorEntry` на `AccessEntry`.

### Что удаляется

| Символ | Где | Почему |
|---|---|---|
| `asyncScopeRoot`, `AsyncScopeRoot` | `async_scope_root.dart` (файл целиком + `part`-директива) | роль переходит к координатору |
| `AsyncScopeCoordinatorEntry` | `async_scope_coordinator.dart` | переезжает в ядро как `AccessEntry`, из публичного API уходит |
| `ScopeChildEntry` | `async_scope_parent.dart` | переезжает в ядро как `ChildEntry`, из публичного API уходит |
| `_AsyncScopeCoordinatorQueue.close()` | там же | мёртвый код; при владении экземпляром не нужен |

Меняется сигнатура публичного `AsyncScopeParent.waitForChildren()` — у него
появляются именованные `timeout` и `onTimeout`. Это ломает тех, кто его
переопределял или вызывал с прежней сигнатурой; в CHANGELOG идёт отдельным
пунктом `[breaking changes]`.

## Ошибки и краевые случаи

- **`scopeKey` без координатора** — та же `FlutterError` с той же
  формулировкой, что и сейчас.
- **Скоуп без родителя и без координатора** — регистрации не происходит,
  ждать его некому. Это осознанная замена молчаливой регистрации в глобальном
  корне; фиксируется в dartdoc `AsyncScopeParent` и в CHANGELOG.
- **Таймаут очереди** — сообщить через `FlutterError.reportError` и всё равно
  пустить владельца: иначе поддерево зависает навсегда. Политика не меняется.
- **Таймаут ожидания детей** — сообщить и продолжить утилизацию. Не меняется.
- **Снятие координатора с дерева** — специальной обработки нет и не должно
  быть. Flutter размонтирует детей раньше родителя; очереди умирают вместе с
  элементом; записи, чья асинхронная утилизация ещё доигрывает, держат ссылку
  на свою очередь сами, поэтому их `exit()` отработает штатно уже на
  «осиротевшей» очереди. Принудительно будить или отменять ожидающих нельзя —
  это оборвало бы корректно идущую утилизацию.

## Тестирование

**Юнит-тесты ядра** (`test/scope_coordination_test.dart`, без Flutter):

- вход в пустую очередь завершается немедленно;
- второй вошедший ждёт, пока первый не вызовет `exit`;
- порядок FIFO при трёх и более участниках;
- выход не по порядку (второй вышел раньше первого) не пропускает третьего
  раньше времени;
- `cancel` во время ожидания прекращает ожидание, `isCancelled` истинно,
  запись остаётся в очереди до `exit`;
- таймаут зовёт `onTimeout` и пропускает владельца дальше;
- очередь удаляется из карты, когда вышел последний (`length`, `containsKey`);
- повторный вход по тому же ключу после опустошения создаёт новую очередь;
- `waitForChildren` без детей завершается немедленно;
- `waitForChildren` ждёт `unregister` каждого ребёнка;
- таймаут `waitForChildren` зовёт `onTimeout` и завершается нормально;
- реестр очищается после `waitForChildren`.

**Widget-тесты** (`test/async_scope_coordinator_test.dart`):

- два координатора с одинаковым ключом не блокируют друг друга;
- при вложенных координаторах ключ обслуживает ближайший;
- `scopeKey` без координатора в дереве даёт `FlutterError`;
- скоуп регистрируется у ближайшего `AsyncScopeParent` — у родительского
  скоупа, если он есть, иначе у координатора;
- скоуп без родителя и координатора монтируется и утилизируется без ошибок.
