## P2 №8 — `data` отдавал `null`, которого скоуп не выдавал

```dart
T get data => switch (_data) {
      final T data => data,
      _ => throw StateError('Not initialized'),
    };
T? _data;
```

Геттер спрашивал само значение, готово ли значение. Для nullable `T` — скажем,
`AsyncDataScope<String?>` — исходный `null` совпадает с образцом `final T data`,
и до окончания инициализации `data` возвращал `null` вместо обещанного
`StateError`. Контракт в `AsyncDataScopeContext` при этом говорит прямо:
«Throws a [StateError] before the scope is ready».

Готовность вынесена в отдельное поле:

```dart
T get data => _hasData ? _data as T : throw StateError('Not initialized');
bool _hasData = false;
```

Сообщение ошибки оставлено прежним: оно дословно записано в
`doc/f_async_data_scope.md` и в русском зеркале.

Два теста в `test/async_data_scope_test.dart`, группа «AsyncDataScope with a
nullable value»: до прихода значения `data` бросает; после `AsyncDataScopeReady(null)`
— возвращает `null`. Второй существует именно затем, чтобы правка не превратилась
в «бросать всегда»: он был зелёным и до неё.

## P2 №9 — селектор оставался подписанным после того, как виджет его бросил

`_updateDependencies` **добавляла** пару `(value, selector)` к тому, что
зависимый выбрал в прошлых сборках, а список очищался только после уже
найденного изменения. Виджет, читавший в одной сборке `value`, а в следующей
`other`, оставался подписан на оба — и изменение `value`, которого он больше не
читает, его перестраивало. Ровно то, для чего селекторы и существуют.

### Почему это оказалось не однострочной правкой

Список должен принадлежать **сборке**, а не зависимому. Границу сборки Flutter
не сообщает: `dependOnInheritedElement` вызывается из `build()` зависимого, но
хука «зависимый начинает сборку» нет — по этой же причине накапливает аспекты и
собственная `InheritedModel` фреймворка. Проверенные и отвергнутые опоры:

- **`Element.dirty`** — во время `build()` всегда `true` (`_dirty` сбрасывается
  в `finally` после `build()`), так что переход «чистый → грязный» из точки
  регистрации не виден;
- **идентичность `dependent.widget`** — покрывает только перестроение сверху; при
  `setState` виджет тот же;
- **`InheritedElement`** — ни одного подходящего хука: `updateDependencies`,
  `notifyDependent`, `removeDependent`, и всё;
- **`Element._dependencies`** фреймворка чистится только в `activate()`.

Взята граница кадра: зависимый регистрируется только пока строится, а две его
сборки разделены кадром.

```dart
Object _buildPass = Object();
bool _buildPassEnding = false;

Object _currentBuildPass() {
  if (!_buildPassEnding) {
    _buildPassEnding = true;
    SchedulerBinding.instance.addPostFrameCallback((_) {
      _buildPass = Object();
      _buildPassEnding = false;
    });
  }

  return _buildPass;
}
```

Список зависимого стал объектом `_ScopeDependencies`, который помнит свою
сборку и сбрасывается, когда приходит регистрация из следующей. Флаг «подписан
на всё» (`of(listen: true)` без селектора) переехал из «список пуст» в явное
поле `all`: после сброса список тоже пуст, и различать это по длине больше
нельзя.

`addPostFrameCallback` кадра не планирует. Это и не нужно: сборка идёт внутри
кадра, а без кадра нет и новых регистраций.

### Что этим **не** закрывается

Зависимый, перестроенный **дважды за один кадр**, сохранит оба набора
селекторов — граница кадра этот случай не различает, и цена ему прежняя: одна
лишняя сборка. Собственное уведомление скоупа сюда не относится: там
регистрация обнуляется до перестроения зависимого. Записано в
`doc/b_scope_widget.md` и в русском зеркале.

### Тесты

Два теста в `test/scope_widget_test.dart`, оба через фикстуру `_CounterScope` с
двумя изменяемыми полями:

- `a dependent that moved to another value is not rebuilt by the old one` —
  `_SwitchingText` переходит с `value` на `other`; изменение `value` его больше
  не трогает, изменение `other` — трогает. До правки: 3 сборки вместо 2;
- `a dependent of two values is rebuilt by either of them` — `_BothText`
  выбирает оба значения в одной сборке. Этот тест написан **после** правки и
  ради неё: механизм «одна сборка — один набор» можно испортить и в другую
  сторону, оставив только последний селектор, и это был бы пропущенный
  перестрой — хуже лишнего.

**Мутационная проверка, три мутации, каждая роняет ровно один тест:** убрать
сброс на новой сборке (возврат к накоплению); выдавать новую сборку на каждую
регистрацию (остаётся последний селектор); перестать учитывать `all`.
